# 중력정비반 개인 프로젝트 기획서

2인 온라인 협동 물리 액션 퍼즐 게임

작성일 2026년 10월 26일 · 초안 1.0

## 1 기획 의도

고장 난 자동화 시설에 투입된 두 정비사가 중력 장갑으로 화물을 옮기고 기계를 재가동하며, 폭주한 경비 로봇을 제압하고 탈출한다. 같은 상자가 이동 발판이 되고, 압력판의 추로 쓰이며, 전투에서는 엄폐물과 투사체가 된다. 물리를 이용해 두 사람이 해결 방법을 찾는 과정이 게임의 중심이다.

첨부 채용 공고의 담당 업무 3개, 자격조건 4개, 우대사항 8개를 모두 검토 대상으로 삼는다. 기능을 따로 나열하는 데 그치지 않고 플레이, 콘텐츠 제작, 검증 자료로 연결한다. 이 문서는 구현 전 계획이며, 개발 경력이나 이미 검증한 성과를 의미하지 않는다.

### 경력 조건의 취급

이 프로젝트를 완성하더라도 Unity 실무 5년이라는 기간 조건이 생기는 것은 아니다. 지원 시 실제 경력 기간과 이 프로젝트의 직접 기여 범위를 각각 기재한다. 자격조건 충족 여부와 포트폴리오의 기술적 완성도는 별도로 판단한다.

### 현재 프로젝트에서 확인한 출발점

프로젝트 설정 파일에서 엔진과 URP 버전을 확인했다. 패키지 목록에는 Input System, AI Navigation, Test Framework가 있으며, Netcode for GameObjects와 Addressables는 직접 의존성으로 기재되어 있지 않다. 설치나 설정 변경은 하지 않았다. 1주차에 필요한 패키지의 호환 조합을 작은 연결 실험으로 검증하고 버전을 고정한다.

### 콘솔 경험을 충족하기 위한 별도 조건

패드가 작동하는 Windows 게임만으로 콘솔 개발 경험을 충족했다고 적지 않는다. 실제 콘솔 경험을 얻으려면 플랫폼 개발자 승인, 해당 플랫폼 빌드 지원과 SDK 사용 권한, 필요한 라이선스 및 개발 장비 등 접근 조건을 먼저 확인해야 한다. [자료 5]

접근이 확보되면 목표 콘솔 한 기종을 선택해 빌드·배포·실기 실행, 패드 연결 해제, 사용자 전환, 저장, 일시 중단과 복귀를 검증한다. 필요한 플랫폼별 심사 항목도 확인한다. 권한이 없으면 상태를 **콘솔 대응 설계와 PC 패드 검증 완료, 콘솔 실기 경험 미충족**으로 남긴다. 승인 대기와 실기 대응 기간은 기본 12주 추정에 포함하지 않는다.

## 5 플레이 구조와 세 구역

### 기본 플레이 흐름

방 생성과 참가 → 두 사람 준비 → 시설 진입 → 장치 관찰과 역할 분담 → 물체 조작 → 전투와 퍼즐 결합 → 체크포인트 → 다음 구역 → 탈출 결과 화면 순서로 진행한다. 역할은 고정 직업으로 나누지 않고 두 플레이어가 같은 능력을 가진다.

### 구역 1 화물 집하장

잡기와 놓기, 밀쳐내기를 익힌다. 한 사람은 상자를 중량 압력판에 올려 문을 열고, 다른 사람은 열린 통로에서 코어를 가져온다. 회수 후 두 사람이 출구에 도착하면 완료한다. 압력판 위 물체가 흔들려 문이 반복 개폐되지 않도록 작동·해제 기준과 짧은 유지 시간을 둔다.

### 구역 2 정비 교량

중력 장갑으로 화물을 경첩 다리의 추 받침에 옮겨 다리를 내린다. 한 사람이 건너가 고정 레버를 작동하면 다른 사람도 안전하게 통과한다. 이어지는 운반대에서는 한 사람이 장치를 조작하고 다른 사람이 전력 코어를 옮긴다. 동시에 같은 물체를 잡을 수는 없다. 협동은 서로 다른 장치와 공간의 역할 분담으로 만든다.

### 구역 3 중앙 전력실

한 사람이 운반대를 조작해 코어를 이동시키고, 다른 사람은 경비병을 상대한다. 돌진병을 경첩 방벽으로 유도해 잠시 무력화하면 운반 시간이 생긴다. 코어를 소켓에 고정하고 두 사람이 서로 다른 재가동 스위치를 유지하면 탈출문이 열린다. 적을 모두 처치하는 방법과 환경 장치를 이용하는 방법을 함께 제공한다.

### 실패와 복구

플레이어 체력이 소진되면 다운되며 동료가 3초간 상호작용해 구조한다. 둘 다 다운되면 최근 체크포인트를 복구한다. 필수 물체가 낙하하거나 회수 불가능 영역에 머물면 잡기를 해제하고 지정 복구 위치로 반환한다. 구역 재시작은 체력, 적, 물체 위치와 속도, 연결, 장치 상태를 함께 초기화한다.

### 조작과 화면 정보

키보드는 이동·점프·상호작용·공격·잡기·밀쳐내기를 각각 독립 입력으로 제공한다. 패드는 왼쪽 스틱 이동, 오른쪽 스틱 카메라, 트리거 잡기, 범퍼 밀쳐내기를 기본안으로 삼고 테스트로 조정한다. 화면에는 동료 상태, 잡을 수 있는 대상, 무게 제한, 장치 작동 원인과 연결 상태를 표시한다. 색상 외에 아이콘과 형태를 함께 사용한다.

## 6 물리 시스템 상세

### 플레이어와 중력 장갑

플레이어 이동은 회전을 제한한 동적 Rigidbody와 캡슐 충돌체로 구현한다. 입력을 수집한 뒤 고정 물리 갱신에서 목표 수평 속도와 지면 상태를 처리한다. 지면 감지, 경사 제한, 낮은 턱 처리와 낙하 복구를 포함한다. 움직이는 발판에서는 지지체의 이동 속도를 반영한다. 기본 애니메이션의 루트 모션은 끄고 이동 판정과 시각 표현의 책임을 구분한다.

장갑은 조준한 물체를 일정 거리에서 붙잡는다. 호스트가 거리, 가시선, 질량, 점유 여부를 확인한 뒤 물체와 호스트의 비충돌 운동학적 앵커를 ConfigurableJoint로 연결한다. 앵커를 물리 갱신에서 이동하고 구동력·거리·각도 제한을 둔다. 물체를 프레임마다 순간이동시키는 방식은 쓰지 않는다. 놓기, 다운, 연결 종료, 구역 변경 시 연결을 해제한다. [자료 1·2]

| 장치 | 플레이 규칙 | 안정성과 예외 처리 |
| --- | --- | --- |
| 중량 압력판 | 유효 물체의 합산 질량이 기준 이상이면 작동 | 물체별 중복 콜라이더 제거, 작동·해제 기준 분리 |
| 경첩 다리 | 추의 힘으로 회전하고 레버로 고정 | HingeJoint 각도 제한, 고정 해제 순서 정의 |
| 화물 운반대 | 한 사람이 스위치를 유지하면 지정 경로 이동 | 운동학적 강체로 이동, 이탈 물체 복구, 승객 이동 검증 |
| 전력 코어 소켓 | 올바른 코어가 범위·속도 조건을 만족하면 결합 | 결합 시 잡기 해제 후 고정, 중복 결합과 중복 보상 차단 |

### 초기 조정값과 검증

최초 실험값은 잡기 거리 3m, 조작 가능 질량 5~40kg, 동시 잡기 1인 1개, 물리 갱신 50Hz, 상태 전송 20Hz다. 확정 사양이 아니며 1~2주차에 지연과 조작감을 비교해 조정한다. 질량 차이를 과도하게 키우지 않고 필요한 물체에만 연속 충돌 검사를 적용한다.

필수 물리 물체는 구역당 12개 이내, 동시에 움직이는 대상은 8개 이내를 초기 예산으로 잡는다. 물리 결과가 다른 PC에서 저절로 같아진다고 가정하지 않는다. 호스트가 실제 물리를 계산하고 참가자는 전달받은 상태를 표시한다. 지터, 관통, 과도한 발사 속도, 연결 잔존을 반복 재현해 원인과 수정 결과를 기록한다.

## 7 전투와 몬스터 및 애니메이션

### 전투 규칙

기본 근접 공격은 예고, 유효 판정, 회복 구간을 가진다. 공격을 시작할 때 공격 식별자를 발급하고 같은 공격으로 같은 대상에 두 번 피해를 주지 않는다. 대상 목록은 재사용하며 공격 도중 새로운 입력을 받을 수 있는 구간과 피격으로 취소되는 구간을 데이터로 정한다.

물체 공격은 가벼운 접촉과 유효 충돌을 구분한다. 초기에는 상대 속도와 질량을 이용한 튜닝용 충격 점수를 기준으로 삼되, 피해량과 최대값을 제한한다. 이는 실제 충격량의 정확한 물리 계산이라고 주장하지 않는다. 짧은 재피격 제한과 물체·대상 쌍 식별자로 접촉 반복 피해를 막는다. 아군 피해는 끄고 적에게만 적용한다.

### 적 두 종류

**경비병**은 순찰, 탐지, 추적, 공격 예고, 근접 공격, 회복, 피격, 사망으로 전이한다. 시야가 막히거나 목표가 너무 멀어지면 마지막 확인 지점까지 이동한 뒤 복귀한다. 공격 중에는 목표를 계속 바꾸지 않는다.

**돌진병**은 목표를 정하고 바닥에 공격 범위를 보여준 뒤 돌진한다. 돌진 방향은 예고 종료 시 확정하며, 방벽이나 무거운 물체에 부딪히면 무력화된다. NavMesh 이동과 물리 돌진이 동시에 위치를 제어하지 않도록 상태 전환 시 제어 주체를 바꾼다. 길이 막히면 일정 시간 후 재탐색하거나 복귀한다.

### Animator 설계

기본 레이어는 대기·이동·점프·착지, 상체 레이어는 잡기 자세와 팔 조작을 담당한다. 상체에는 Avatar Mask를 적용한다. 공격과 피격의 전이 우선순위를 정하고 사망은 일반 이동으로 복귀하지 않는 종료 상태로 둔다. 잡는 물체가 사라지거나 연결이 끊길 때 상체 상태를 정리한다.

호스트의 전투 상태와 시작 시각을 기준으로 양쪽에서 애니메이션을 표현한다. 실제 피해 판정은 호스트의 공격 시간표로 계산하고, 클립 이벤트는 효과음과 연출에 사용한다. 피격·다운·구조·사망 전환 시 판정과 화면 상태가 어긋나는지 검증한다.

### 전투 완료 기준

두 PC에서 동일한 체력과 적 사망 결과가 유지되고, 같은 공격의 중복 피해가 없어야 한다. 벽 너머 공격, 공격 중 목표 소실, 두 사람의 동시 타격, 물체가 적에 계속 닿아 있는 상황을 테스트한다. 전투 웨이브는 최대 적 4마리로 제한한다.

## 8 온라인 협동과 권한 설계

기본안은 Netcode for GameObjects, Unity Transport, Multiplayer Services SDK의 Relay 연동이다. 정확한 패키지 버전은 현재 엔진에서 설치·빌드 실험 후 고정한다. Relay는 인터넷 연결 경로를 제공하며 게임 판정은 호스트가 맡는다. 참가 코드 방식으로 시작하고 공개 매칭은 만들지 않는다. 서비스 설정, 사용 한도와 비용 조건은 구현 시 확인한다. [자료 3]

### 연결과 구역 전환

방 생성 → 코드 참가 → 프로토콜·콘텐츠 버전과 2인 정원 확인 → 두 사람 준비 → 양쪽 구역 로딩 → 로딩 완료 확인 → 호스트가 플레이 시작을 승인한다. 진행 중 새 참가와 자동 재접속은 기본 범위에서 제외한다. 로딩 실패나 30초 시간 초과에는 오류 원인을 표시하고 방으로 복귀한다.

### 호스트가 결정하는 상태

물리 물체와 Joint, 적 AI, 공격 피해, 체력, 장치 성공, 체크포인트, 스폰과 제거를 호스트가 결정한다. 플레이어 이동도 입력을 호스트에 보내 처리하는 방식으로 시작한다. 로컬 카메라와 조준 표시는 즉시 반응시킨다. 전신 물리 예측과 롤백은 기본 범위에 넣지 않으며, 참가자 이동감은 지연 실험의 필수 통과 항목으로 둔다. [자료 4]

| 상황 | 처리 규칙 |
| --- | --- |
| 두 사람이 같은 물체를 잡음 | 호스트가 처리한 첫 유효 요청만 점유 승인하고 다른 요청은 거절 |
| 잘못된 상호작용 요청 | 접속자, 거리, 가시선, 현재 상태, 재사용 간격을 호스트에서 검사 |
| 오래되거나 중복된 요청 | 요청 순번과 상태 버전으로 중복 실행과 이전 상태 적용 방지 |
| 물체를 잡은 참가자가 종료 | 연결 해제, 물체 점유 해제, 진행 중단 안내 후 방 복귀 |
| 호스트가 종료 | 세션 종료와 오류 안내 · 호스트 이전 기능은 기본 범위에서 제외 |
| 이벤트를 늦게 수신 | 문 열림과 코어 결합 등 지속 상태는 최신 값으로 복구 |

### 동기화와 지연 목표

참가자는 물리 물체를 별도로 경쟁 시뮬레이션하지 않고 호스트 상태를 보간한다. 영속 상태는 복제 상태값으로, 타격 효과 같은 일회성 표현은 이벤트로 전달한다. 요청 순번, 객체 식별자, 판정 시각과 거절 사유를 기록한다.

왕복 지연 0·80·150ms 및 패킷 손실 1% 조건을 시험한다. 80ms에서 필수 퍼즐과 전투를 반복 완주하는 것을 목표로 하고, 150ms는 상태 일관성과 복구 확인 및 조작감 한계 측정에 사용한다. 초기 호스트 이동 방식이 80ms에서 불편하면 2주차에 이동 예측의 추가 비용을 판단하고, 먼저 이동 속도와 전투 반응 요구를 조정한다.

## 9 콘텐츠 제작 도구와 설계 구조

### 퍼즐 연결 편집기

전용 EditorWindow에서 장치를 배치하고 입력 조건과 출력 동작을 연결한다. 예를 들어 압력판과 레버가 모두 활성화되면 문이 열리도록 구성한다. 모든 조건 충족과 하나 이상 충족을 기본 조합으로 제공한다. 장치 정의는 ScriptableObject, 장면 배치는 프리팹과 배치 데이터, 현재 작동 여부는 런타임 상태에 보관한다.

편집기는 잘못된 참조, 중복 식별자, 출구 조건 누락, 지원하지 않는 순환 연결, 필수 코어 복구 위치 누락을 검사한다. 그래프 순환과 연결 누락 검사는 구조 검증이며 퍼즐을 실제로 풀 수 있다는 증명은 아니다. 플레이 테스트로 해결 가능성을 별도 확인한다. Undo, 장면 변경 표시, 프리팹 저장 경계를 지원한다.

### 전투 웨이브 편집기와 디버그 화면

적 종류, 수, 스폰 위치, 시작 조건을 편집하고 배치 위치와 상한을 검사한다. 실행 중에는 장치 식별자, 현재 조건, 점유 플레이어, AI 상태, 요청 거절 이유를 표시한다. 개발 도구는 편집 전용 어셈블리로 분리해 일반 플레이 화면과 배포 빌드에 노출하지 않는다.

### SOLID를 적용하는 책임 경계

입력은 명령을 만들고, 게임 규칙은 명령을 판정하며, 네트워크 어댑터는 전달을 담당한다. UI는 상태를 읽어 표시한다. 물리 상호작용, 피해 수신, 조건 평가, 자원 로딩은 작은 계약으로 나눈다. 단순한 클래스마다 인터페이스를 추가하지 않고 테스트나 구현 교체가 필요한 경계에 적용한다.

새 장치는 공통 조건·동작 계약을 구현해 등록하며 기존 장치 판정기를 계속 수정하지 않도록 한다. 네트워크 메시지나 엔진 객체에 종속되지 않는 조건 평가와 중복 판정은 일반 C# 로직으로 두어 테스트한다. 저장은 체크포인트의 의미 상태를 기록하고 구역 복구 시 호스트가 재구성한다. 물리 엔진 전체 상태를 정밀 재현하는 저장은 목표가 아니다.

### 도구 생산성의 검증

같은 난도의 소형 퍼즐 두 개를 수동 설정과 편집기 방식으로 제작한다. 배치부터 오류 없는 플레이 시작까지의 시간, 누락 참조 수, 수정 횟수를 기록한다. 사용자의 도구 숙련도와 콘텐츠 차이를 함께 적고, 측정 전에는 생산성 향상 수치를 주장하지 않는다.

변수는 카멜 표기법, 함수와 매개변수는 파스칼 표기법을 적용한다. Unity 생명주기 함수 등 외부에서 정한 이름은 해당 규약을 따른다.

## 10 자원과 그래픽스 및 AI 활용

### Addressables와 메모리 수명

시작 장면은 접속 UI와 전역 서비스만 유지한다. 시설 구역 장면과 구역 전용 적·효과를 Addressables로 로드한다. 공통 자원과 구역 전용 자원을 나누고 직접 참조로 구역 자원이 상시 로드되지 않는지 확인한다. 호스트가 장면 전환을 지휘하고 양쪽의 로딩 완료를 확인한다.

기본안은 NGO 장면 관리와의 충돌을 줄이기 위해 고정된 게임플레이 네트워크 루트를 유지하고, 구역 환경을 Addressables로 로드한 뒤 동적 네트워크 객체를 호스트가 생성하는 방식이다. 네트워크 프리팹은 접속 전에 양쪽이 같은 목록을 등록한다. 이 통합 방식의 실행 빌드 검증을 1주차 위험 실험에 포함한다.

핸들을 획득한 서비스가 해제를 책임지고, 장면 종료·실패·연결 종료 시 정리한다. 로딩을 취소해도 이미 시작한 실제 작업이 즉시 중단된다고 가정하지 않는다. 늦게 완료된 결과를 현재 장면에 적용하지 않고 확보된 자원을 정리한다. 풀링 객체가 자원을 참조하면 풀을 먼저 비운다. 참조 해제와 실제 번들 메모리 해제의 시점은 구분한다. [자료 6]

### 자료구조와 C# 검증

식별자 조회에는 사전, 타격 중복과 압력판 물체 집계에는 집합, 요청 대기에는 큐를 사용한다. 퍼즐 연결은 인접 목록으로 표현하고 깊이 우선 탐색으로 순환을 검사한다. 구역 크기에 맞는 단순 구조를 선택하고 평균 조회 비용과 최악 상황을 설명한다. AI 탐색은 NavMesh를 활용하며 직접 A*를 구현했다고 주장하지 않는다.

이벤트 구독 해제, 비동기 완료 후 파괴된 대상 접근, 반복 로딩, 풀 초기화를 점검한다. 반복 판정에서 임시 컬렉션과 문자열 할당을 줄이고 Profiler로 확인한다. 알고리즘을 썼다는 사실과 실제 병목 개선을 구분한다.

### 그래픽스 구현과 측정

조작 대상 표시와 돌진 예고 영역을 URP 셰이더로 구현한다. 깊이에 가려지는 대상의 표현 규칙, 투명 효과의 겹침, 머티리얼 인스턴스 증가를 검증한다. 환경은 사전 계산 조명 중심으로 만들고 동적 그림자와 효과 수에 예산을 둔다. Frame Debugger와 CPU·GPU 측정으로 배칭, 드로 호출, 투명 오버드로를 확인한다.

### 개발 보조 AI의 사용

게임 속 몬스터 AI와 개발 보조 AI를 별개 항목으로 기록한다. 생성형 AI는 테스트 누락 사례 제안과 도구 코드 초안에 사용한다. 사람이 API 존재 여부, 수명 관리, 권한 검증을 검토하고 채택 전 테스트한다. 질문, 채택·기각 이유, 수정 내용, 발견한 결함과 소요 시간을 남겨 품질·생산성 효과를 검증한다. 미검증 결과를 그대로 성과로 기재하지 않는다.

| 8주 | Addressables 전환 완성, 취소와 실패, 풀 관리 | 반복 전환과 연결 종료 시 자원 정리 |
| 9주 | 셰이더, 조명, 패드 UI, 디버그 계측 | 두 입력 방식 완주와 렌더링 측정 확보 |
| 10주 | 네트워크·메모리·예외 상황 집중 검증 | 상태 불일치와 진행 불가 결함 수정 |
| 11주 | 콘텐츠 다듬기, 성능 개선, 도구·AI 비교 측정 | 최종 후보 빌드와 비교 자료 |
| 12주 | 회귀 확인, 영상, 문서와 기여 범위 정리 | 배포 가능한 PC 빌드와 제출 자료 묶음 |

### 주요 위험과 대응

가장 큰 위험은 물리와 멀티플레이의 결합이다. 첫 2주에 검증하고 실패하면 장치 수보다 먼저 동시 물리 물체 수, 이동 속도, 전투 속도를 낮춘다. Joint 떨림은 질량 비율·힘 제한·갱신 순서를 비교해 조정한다. 자원 전환과 네트워크 생성 순서 충돌은 1주차에 실험한다.

일정이 밀리면 장식용 방, 외형 종류, 연출 길이부터 줄인다. 2인 멀티, Joint 물리 퍼즐, 전투와 AI, 에디터 도구, Animator, Addressables, 그래픽스 검증, AI 검증 기록은 유지한다. 그래도 부족하면 일정을 연장한다. 공개 매칭, 3인 이상, PvP, 호스트 이전, 자동 재접속, 성장·제작 시스템은 기본 범위에 추가하지 않는다.

성능 수치는 목표이며 현재 측정 결과가 아니다. PC 사양, 빌드 종류, 품질 설정, 물리 대상 수와 적 수를 함께 기록한다. 캐시와 번들 공유 때문에 메모리가 정확히 최초 값으로 돌아온다고 가정하지 않고, 반복 후 안정화와 미해제 참조를 조사한다. 로컬 두 프로세스 테스트와 실제 별도 PC의 인터넷 테스트도 구분한다.

### 최종 제출 묶음

실행 빌드와 접속 방법, 3분 내외 플레이 영상, 1분 내외 제작 도구 영상, 시스템 구조도, 공고 15항목 대응표, 네트워크·물리·성능 문제 해결 사례, 검증 결과표를 준비한다. 외부 에셋과 생성형 AI 사용 범위, 직접 설계·구현한 범위, 실제 경력 및 콘솔 검증 상태를 명시한다.

### 참고 자료와 확인 범위

채용 조건은 사용자가 첨부한 이미지 2장을 기준으로 정리했다. 기술 문서는 설계 근거이며 현재 프로젝트의 API·패키지 호환성 검증을 대신하지 않는다. 아래 링크는 2026년 10월 26일 확인했다.

- 자료 3 온라인 세션과 중계 [Unity Relay와 NGO 연동](https://docs.unity.com/en-us/mps-sdk/tutorials/relay-and-ngo)
- 자료 4 호스트 물리 권한의 기본 개념 [Unity NGO Physics](https://docs-multiplayer.unity3d.com/netcode/1.8.1/advanced-topics/physics/) 구버전의 개념 자료로만 사용
- 자료 5 콘솔 접근 조건 [Unity Console Development](https://unity.com/solutions/console)
- 자료 6 참조와 메모리 해제 [Unity Addressables Memory Management](https://docs.unity3d.com/Packages/com.unity.addressables@2.7/manual/MemoryManagement.html)

현재 확인한 로컬 파일은 ProjectSettings/ProjectVersion.txt와 Packages/manifest.json이다. 이번 작업은 기획서 작성이며 게임 구현, 패키지 설치, 콘솔 권한 확인 또는 실제 플레이 검증은 수행하지 않았다.
