# 중력정비반 개인 프로젝트 기획서

2인 온라인 협동 물리 액션 퍼즐 게임

2026년 10월 26일 · 수정안 1.2 · 무료 파일 검수 완료 및 A안 캐릭터 적용 검수 대기

## 1 목표와 개발 범위

두 정비사가 중력 장갑으로 상자를 옮기고 고장 난 시설을 복구한다. 같은 상자가 압력판의 추가 되고, 경첩 다리를 내리며, 전투에서는 엄폐물과 공격 수단으로 쓰인다. 물리 퍼즐과 전투를 2인 협동 안에 연결하고, 이를 제작하는 작은 에디터 도구까지 직접 구현한다.

공고의 담당 업무 3개, 자격조건 4개, 우대사항 8개를 모두 검토한다. 실제 Unity 실무 연차와 콘솔 기기 경험은 개발 기능으로 대체하지 않는다. 문서는 구현 계획이며 현재 기능이나 성능을 달성했다는 보고가 아니다.

기존 3구역·장치 4종·편집기 2종의 범위를 줄인다. 2인·방 2개·퍼즐 장치 2종·적 2종으로 완주 가능한 소형 게임을 만든다. 퍼즐과 웨이브는 하나의 편집 창에서 탭으로 관리한다. 공고 대응 기술은 유지하고 반복 콘텐츠와 도구의 복잡도를 줄이는 결정이다.

## 4 두 방의 플레이와 복구

방 생성 → 코드 참가 → 두 사람 준비 → 화물실 → 방 전환 → 정비 교량 → 공동 출구 도달 순서로 진행한다. 두 플레이어는 같은 능력을 사용하고 상황에 따라 역할을 바꾼다. 싱글플레이, 3인 이상, 공개 매칭, 호스트 이전과 중도 참가는 기본 범위에 넣지 않는다.

**방 1 화물실**에서는 상자를 잡고 압력판에 올려 통로를 연다. 한 사람이 통로를 건너 다리 고정용 정비 권한을 활성화하고 돌아오면 두 사람이 다음 출구로 이동한다. 이 권한은 일반 상호작용 상태이며 별도 퍼즐 장치 종류를 추가하지 않는다. 압력판은 플레이어를 제외한 유효 물체의 질량을 집계한다.

**방 2 정비 교량**에서는 화물을 추 받침에 놓아 다리를 내린다. 한 사람은 다리를 건너 고정 장치를 작동시키고, 다른 사람은 경비 유닛을 상대한다. 돌진병을 방벽으로 유도하면 무력화 시간이 생긴다. 두 사람 모두 출구에 도착하면 완료한다. 동일 물체의 공동 잡기는 지원하지 않으며 역할 분담으로 협동을 만든다.

체력이 0이면 다운된다. 동료가 3초간 상호작용하면 체력 40으로 구조한다. 둘 다 다운되면 해당 방 체크포인트로 복구한다. 구조자도 피격되거나 거리가 멀어지면 구조가 취소된다. 필수 물체가 낙하·회수 불가 상태가 되면 점유와 Joint를 해제하고 복구 위치에 반환한다. 초기화는 위치·속도·장치·적·체력·진행 상태를 함께 복구한다.

키보드와 마우스 및 게임패드를 지원한다. 화면은 동료 상태, 조작 대상, 무게 제한, 장치 작동 원인과 연결 상태를 표시한다. 색상 외에 아이콘과 형태를 함께 사용한다. A안인 Synty 로우폴리 방향을 검수 기준으로 삼되, 원본 팩의 외형과 제작 리소스는 실제 확인 후 확정한다.

## 5 물리와 보간 명세

입력은 매 화면 갱신에서 수집하고 호스트의 고정 물리 갱신에서 적용한다. 플레이어는 회전을 제한한 동적 Rigidbody와 캡슐 충돌체를 사용한다. 지면·경사·낮은 턱·낙하를 처리하고, 이동 애니메이션은 기본적으로 루트 모션을 끈다. 호스트가 이동과 실제 충돌을 판정한다.

잡기는 거리·시야·질량·점유·플레이어 상태를 확인한 뒤 호스트가 승인한다. 비충돌 운동학적 앵커와 물체를 ConfigurableJoint로 연결하고 앵커를 물리 갱신에서 MovePosition으로 이동한다. 힘과 최대 거리·속도를 제한하며 Transform을 매 프레임 직접 덮어쓰지 않는다. 놓기·다운·퇴장·방 전환·복구 시 Joint를 해제한다.

| 항목 | 초기 설계값 | 확인 방법 |
| --- | --- | --- |
| 물리와 전송 | 물리 50Hz · NGO 입력·상태 갱신 30Hz | 30·60·120fps에서 조작과 상태 비교 |
| 이동과 점프 | 이동 3.5m/s · 점프 초기 수직 속도 5m/s · 경사 45도 | 경사·턱·착지·밀림 시험 |
| 잡기 | 최대 3m · 5~40kg · 1인 1개 · 구역당 동적 물체 최대 8개 | 이중 점유·벽 관통·강제 이탈 시험 |
| 압력판 | 작동 8kg · 해제 6kg · 유지 0.2초 | 다중 콜라이더, 경계 질량, 흔들림 시험 |
| 다리 | HingeJoint 회전 범위 0~65도 · 고정은 별도 상태 | 진입·이탈·추 낙하·고정 해제 시험 |

수치는 실험 시작값이다. 질량비·연결 위치·최대 구동력·감쇠는 물체 규격과 함께 튜닝 시트에 기록한다. 단순 스프링 식을 썼다는 이유로 전체 PhysX가 결정적이라고 주장하지 않는다. 네트워크 참가자가 같은 물리를 따로 계산해 결과가 일치한다고 가정하지 않는다.

**표시 보간**은 호스트의 플레이어·잡힌 물체에서 Rigidbody Interpolate를 비교 적용하고, 카메라는 표시되는 플레이어 위치를 추적한다. Interpolate는 물리 갱신 한 번의 표시 지연을 추가한다. 참가자의 비권한 물체는 NGO 상태 보간을 기본으로 하고 Rigidbody 보간을 중복 적용하지 않는다. 앵커 갱신·Joint 판정·표시·카메라 순서를 따로 확인한다. 50Hz와 60fps의 차이 자체를 오류로 보지 않는다. [자료 1]

## 6 전투 수치와 AI 규칙

일반 공격 1종은 근접 공격을 뜻한다. 밀쳐내기는 장갑의 조작 기능이며 자체 체력 피해는 없다. 밀쳐진 물체가 적과 유효 충돌하면 별도 공격 원천으로 피해 파이프라인에 들어온다. 아군 피해는 끈다. 근접과 충돌 피해를 같은 공격 종류라고 혼용하지 않는다.

| 대상 또는 행동 | 초기 수치 | 판정 규칙 |
| --- | --- | --- |
| 플레이어 | 체력 100 · 이동 3.5m/s · 구조 3초 | 다운 시 잡기 해제 · 구조 후 체력 40 |
| 근접 공격 | 피해 20 · 사거리 1.8m · 재사용 0.9초 | 준비 0.25초, 판정 0.12초, 회복 0.4초 |
| 밀쳐내기 | 재사용 1.2초 · 가벼운 대상 속도 상한 8m/s | 직접 피해 없음 · 대상 질량과 상태 검사 |
| 물체 충돌 | 상대 속도 3m/s 이상 · 피해 20~50 | 물체·대상 쌍에 0.5초 재피격 제한 |
| 경비병 | 체력 60 · 이동 2.6m/s · 피해 10 | 공격 예고 0.5초 · 재사용 1.5초 |
| 돌진병 | 체력 100 · 추적 2.2m/s · 돌진 6m/s · 피해 20 | 예고 0.8초 · 돌진 최대 1초 · 충돌 무력화 2초 |

공격 식별자와 피격 대상 집합으로 같은 공격의 중복 피해를 차단한다. 준비 구간은 피격으로 취소할 수 있고, 유효 판정과 회복 구간에는 새 공격을 받지 않는다. 다운은 모든 행동보다 우선한다. 실제 판정은 호스트의 공격 시간표가 담당하고 클립 이벤트는 효과음·연출에 사용한다. 충돌 피해는 튜닝용 점수이며 정확한 충격량 계산으로 주장하지 않는다.

AI는 상태 머신을 사용한다. 경비병은 순찰→탐지→추적→예고→공격→회복을 기본으로 하고 피격·사망을 우선 처리한다. 거리와 시야가 유효한 플레이어 중 가까운 대상을 고르되 현재 목표가 유효하면 최소 1초 유지한다. 시야가 2초 끊기면 마지막 확인 위치로 이동하고, 3초간 도달하지 못하면 재탐색 후 복귀한다.

돌진병은 예고 종료 때 방향을 확정하고 돌진 중에는 꺾지 않는다. NavMesh 이동과 Rigidbody 돌진이 동시에 위치를 제어하지 않게 전환한다. 방벽 충돌·시간 만료·목표 소실·두 사람 동시 타격을 시험한다. 공고 대응을 위해 불필요하게 행동 트리나 자체 A*를 추가하지 않는다.

## 7 Animator 전이와 클립 확보

## 8 온라인 협동과 조작감 통과 기준

NGO·Unity Transport·Multiplayer Services SDK와 Relay의 호환 버전을 최초 실험에서 고정한다. 호스트는 이동·물리·적·피해·진행·스폰을 판정한다. 참가자는 입력과 상호작용 요청을 보낸다. NetworkTransform을 추가하는 것만으로 완전한 예측·되감기·재실행이 생기지 않는다. 기본 범위는 호스트 판정과 표시 보간이며 완전한 물리 예측은 포함하지 않는다. [자료 2]

연속 이동 입력은 순번과 함께 보내 최신 유효 입력을 사용하고, 점프·잡기·놓기는 별도 행동 식별자를 보낸다. 호스트는 접속자·거리·시야·상태·재사용을 확인한다. 카메라와 조준 UI는 로컬에서 즉시 반응하고 실제 이동과 점유 결과는 승인 상태를 따른다. 호스트와 참가자의 반응 차이는 측정해 공개한다.

| 상황 | 처리 | 통과 기준 |
| --- | --- | --- |
| 같은 물체 동시 잡기 | 호스트가 첫 유효 요청만 승인 | 이중 점유 0회 · 거절 원인 표시 |
| 중복·오래된 요청 | 행동 식별자와 상태 버전으로 차단 | 피해·점유·장치 작동이 중복되지 않음 |
| 참가자 또는 호스트 퇴장 | 잡기·Joint·세션 상태 정리 후 방 복귀 | 영구 점유와 잔존 연결 없음 |
| 방 로딩 | 두 사람 완료 확인 후 시작 · 30초 시간 초과 | 실패 시 오류 안내와 자원 정리 |
| 상태 지연 | 지속 상태는 복제값, 연출은 일회성 이벤트 | 문·체력·점유·진행 상태가 최종 수렴 |

1차 기술 실험의 필수 항목은 별도 PC 접속, 상자 한 개 잡기, Joint 해제, 80ms 왕복 지연에서 이동과 잡기, Addressables 자원 한 개 정리다. 해당 실험은 방을 대량 제작하기 전에 진행한다.

왕복 0·80·150ms, 손실 0·1%를 시험한다. 80ms를 기본 수용 조건으로 삼고, 카메라·조준은 다음 표시 프레임 반응, 참가자의 실제 이동 표시 반응은 95백분위 180ms 이내, 잡기 승인 표시는 95백분위 250ms 이내를 초기 목표로 둔다. 최소 30회 행동을 측정하며 입력 시각과 표시 시각을 함께 기록한다. 수치는 체감 보장이 아니므로 실제 플레이 검수도 통과해야 한다.

150ms는 상태 일관성과 복구를 보는 스트레스 조건이며 동일한 쾌적함을 보장하지 않는다. 80ms 조건에서 조작감 검수를 통과하지 못하면 콘텐츠 제작을 멈추고 원인을 분리한다. 입력·전송·보간 버퍼 조정 후에도 실패하면 이동 예측 또는 이동 권한 변경을 별도 설계하고 24~48시간을 다시 산정한다. 일정을 유지하기 위해 실패를 통과로 바꾸지 않는다.

## 9 제작 도구와 SOLID 및 CS 근거

EditorWindow 하나에 퍼즐 탭과 웨이브 탭을 둔다. 퍼즐은 장치 목록·입력 조건·출력 동작을 편집하고 웨이브는 적 종류·수·위치·시작 조건을 편집한다. 노드 그래프 UI, 일반화된 시각 스크립트, 자동 Addressables 그룹 생성은 만들지 않는다. 기본 검증·Undo·SerializedObject·기즈모와 짧은 사용 가이드를 제공한다.

검증기는 참조·식별자·입출구 조건·지원하지 않는 순환·복구 위치·적 상한을 확인한다. DFS 순환 검사는 구조 검증이며 퍼즐 해결 가능성을 증명하지 않는다. 초기 배치와 입력 절차를 명시한 실행 테스트로 실제 완주를 확인한다. 물리만 600회 진행하는 시험은 안정성 보조 시험으로만 사용한다. Physics.Simulate는 FixedUpdate를 호출하지 않으므로 입력·게임 규칙 갱신을 명시적으로 호출해야 한다. [자료 3]

입력 수집, 규칙 판정, 물리 적용, 네트워크 전달, 화면 표시의 책임을 나눈다. 정의는 ScriptableObject, 장면 배치는 프리팹·배치 데이터, 실행 상태는 별도 객체에 둔다. 상호작용·피해·조건·자원 수명의 교체 경계에 작은 인터페이스를 두며 클래스마다 기계적으로 인터페이스를 추가하지 않는다. 편집 코드는 편집 전용 어셈블리에 둔다.

| 구조와 입력 상한 | 비용과 선택 이유 | 메모리 및 확인 |
| --- | --- | --- |
| 장치·객체 사전 · 최대 32개, 초기 용량 64 | 평균 조회 O(1) · 순차 탐색과 비교 | 재해시와 항목별 할당 측정 |
| 공격 대상·압력판 집합 · 최대 8개 | 평균 추가·조회 O(1) · 중복 콜라이더 제거 | 공격 종료·물체 이탈 시 정리 |
| 요청 큐 · 최대 64개 | 추가·제거 O(1) · 초과 시 오래된 이동 병합과 유효 행동 제한 | 무제한 적재 금지 · 최고 점유 기록 |

자료구조의 최악 비용과 충돌·할당 특성도 설명한다. 실제 문제 크기에 맞게 선택하고 자료구조 종류를 늘리는 것을 성과로 삼지 않는다. NavMesh를 사용하면서 자체 A* 구현이라고 주장하지 않는다. NativeArray는 대량 데이터나 Jobs가 필요해졌을 때만 검토하고, 사용한다면 할당자·소유자·작업 완료·Dispose 시점을 함께 정의한다.

## 10 Addressables와 메모리 수명

접속 UI와 고정된 네트워크 게임 루트는 유지하고, 방 1과 방 2의 환경·오디오·정의를 Addressables로 실제 전환한다. 네트워크 프리팹 목록은 양쪽에서 일치시킨 뒤 호스트가 동적 객체를 생성한다. 환경 로딩과 네트워크 장면 관리의 경계는 첫 기술 실험에서 확인한다.

기본 전환 순서는 입력 중단 → 진행과 점유 해제 → Joint 해제 → 네트워크 객체 제거 → 효과 풀 비우기 → 방 참조 해제 → 새 방 로드 → 양쪽 완료 확인 → 호스트 객체 생성과 상태 초기화 → 입력 재개다. 공용 자원은 유지될 수 있으므로 현재 방만 메모리에 남는다고 표현하지 않는다.

초기에는 다음 방 사전 로딩을 하지 않아 최대 메모리와 통합 복잡도를 줄인다. 로딩 지연 때문에 사전 로딩이 필요해지면 현재·다음 방·공용 자원의 동시 점유를 포함해 다시 측정한다. 로드·인스턴스 생성·장면 로드의 획득과 해제 경로를 구분하고 핸들 소유자를 하나로 정한다. 취소 후 늦게 완료된 자원도 정리한다. 참조 해제와 실제 메모리 반환의 시점을 구분한다. [자료 4]

20회 방 왕복 뒤 미해제 핸들, 남은 객체, 풀 크기와 메모리 추세를 확인한다. 최초 캐시 확보 뒤의 안정화 구간을 기준으로 비교하고 강제 GC로 누수를 숨기지 않는다. 최초 진입 10초와 방 전환 4초는 초기 목표이며 콜드·웜 로딩 조건과 저장 장치를 기록한다.

| 물리 | 고정 갱신 한 번당 3ms 이내 | CPU 예산의 일부 · Joint 최악 장면 별도 |
| 드로와 상태 변경 | 드로 호출 500, SetPass 80 이하를 초기 감시선으로 사용 | 초과만으로 실패 판정하지 않고 병목과 함께 판단 |
| 조명 | 그림자 방향광 1개 · 2캐스케이드 · 그림자 맵 1024 | 환경은 베이크 중심 · 동적 그림자 수 제한 |
| 메모리 | 프로세스 전용 바이트 정상 1.5GiB, 전환 최고 2.5GiB 이내 | GPU 전용 메모리는 별도 기록 · 단순 합산 금지 |
| 텍스처와 효과 | 텍스처 512MiB, 동시 타격 효과 8개를 초기 상한으로 사용 | 실제 선택 에셋으로 첫 기준선을 만든 뒤 조정 |
| 관리 할당 | 직접 작성한 반복 판정 경로 0B/프레임 목표 | 로딩·편집·개발 로그는 구분 · 전체 엔진 0B를 주장하지 않음 |

대상 표시와 돌진 예고를 URP 셰이더로 구현하고 깊이 가림·투명 겹침·머티리얼 증가를 확인한다. SRP Batcher는 CPU의 렌더 상태 준비 비용을 줄이는 기능이며 셰이더 연산 비용이나 모든 드로 호출을 없애지 않는다. 최적화 전후의 CPU·GPU·Frame Debugger 캡처로 설명한다. [자료 5]

별도 프로세스 두 개를 같은 PC에 띄운 결과와 두 PC에서 각각 실행한 결과를 구분한다. 프로파일링용 개발 빌드와 배포 후보 빌드의 결과도 함께 남긴다. 숫자를 통과시키기 위해 해상도·품질·물체 수를 바꾸면 비교 조건에 명시한다.

## 14 코딩 규칙

| 구분 | 표기 | 예시 |
| --- | --- | --- |
| 지역 변수와 필드 | 카멜 표기법 | currentHealth, attackId |

Unity 생명주기 함수와 외부 API의 고정된 이름은 해당 규약을 따른다. 아래는 데이터 검증용 순수 함수의 문서 예시이며 실제 전투 구현 전체가 아니다.

```csharp
public bool CanApplyImpact(float ImpactSpeed, float MinimumSpeed)
{
    bool hasValidData = float.IsFinite(ImpactSpeed)
        && float.IsFinite(MinimumSpeed) && MinimumSpeed > 0f;
    return hasValidData && ImpactSpeed >= MinimumSpeed;
}
```
